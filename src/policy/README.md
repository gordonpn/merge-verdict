# Deterministic policy evaluation

`evaluatePolicy` consumes normalized `ReviewSnapshot` and `MergeVerdictConfig` values. It performs no network access, normalization, risk matching, semantic inference, or publication. Import it from `src/policy/index.ts`.

The caller must load configuration and evaluator options from the protected base revision, validate incoming domain values, and pass a final freshly collected head SHA and state fingerprint. The fingerprint must cover all relevant review events, including new comments on unchanged commits. The evaluator compares the supplied identities; it cannot establish that collection was complete or atomic.

The eight conditions reconcile required checks, reviewer completion, unresolved findings, active blocking decisions, reviewer freshness, final snapshot identity, execution errors, and repository-specific constraints. Structured reasons identify the condition, outcome, code, and evidence subject. All reasons are retained with deterministic ordering. Verdict precedence is ERROR, STALE, FAIL, PENDING, PASS.

Missing or old CI evidence and incomplete, rate-limited, skipped, exempt, or stale reviewers remain PENDING. A caller must represent an authorized reviewer exemption by removing that requirement from the effective protected policy; an EXEMPT record alone cannot waive it. Failed reviewer execution and completed CI without a conclusion are ERROR. Older reviewer evidence never causes an overall STALE verdict by itself. A changed final head or fingerprint does.

BLOCKER, HIGH, and MEDIUM findings block by default. `blockingSeverityThreshold: "LOW"` additionally blocks LOW findings. An explicit `"HIGH"` threshold permits non-blocking MEDIUM findings only when advisory exemptions are enabled; HIGH and BLOCKER always block. Advisory findings are exempt only when `allowAdvisoryExemptions` is true and `isBlocking` is false. Callers must supply `unresolvedThreadIds` from the same complete collection as the snapshot. Every unresolved thread must match an unresolved normalized finding by `threadId`; unrelated findings never cover it. Missing identities for a positive count, duplicate identities, count mismatches, and threads without finding coverage fail closed. The optional input preserves compatibility for callers with no unresolved threads. Resolved findings do not block, including findings from older commits. Normalizers must preserve outdated unresolved findings and supply the active, supersession-aware review decision. The evaluator does not infer resolution from comments, passing tests, or commit changes.

The current shared config schema has no custom rule definitions, severity threshold, or permitted CI conclusion list. When `requireCodeEvidence` is true, `codeEvidenceSatisfied` must explicitly attest the caller-evaluated code-evidence requirement: missing yields PENDING and false yields FAIL. This core does not derive that evidence from green CI or resolution comments. `repositoryRules` is an explicit complete list of caller-evaluated constraints; an empty list asserts that no additional constraints apply. `executionErrors` must include collection and normalization errors, with an empty list asserting error-free execution. `permittedCheckConclusions` can explicitly allow neutral or skipped for named checks. These supplemental policy inputs require the same protected-base provenance as config. Cancelled, failure, timed_out, and action_required cannot be permitted.

The result always reports `approvalEligibility: "undetermined"`, including for PASS. A separate risk-tier and approval-provider integration must establish automated approval eligibility and human-review requirements. A PASS from this pure core cannot authorize approval publication by itself. This slice intentionally leaves those integrations, code-evidence collection, and configuration-schema extensions to their owning components.
